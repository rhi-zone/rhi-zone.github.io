## Hologram: Multi-Entity Architecture Sprint

**Scope:** ~120 sessions, predominantly feature exploration and implementation planning for Discord bot's multi-character binding system.

The dominant arc across 2026-01-27 is the emergence of **multi-entity binding** as a first-class concern. Previously, Hologram bound a single entity per Discord channel. The January 27 work redesigns this to support multiple entities responding within the same context, each with independent `$respond` condition evaluation and separate message handling via webhooks.

**Key Architecture Decisions:**

- **Multi-entity binding database schema:** Removing the `UNIQUE (discord_id, discord_type, scope_guild_id, scope_channel_id)` constraint on `discord_entities` table to allow multiple entities per channel
- **Webhook-based message sending:** Each entity sends via its own webhook with custom username and avatar, pulling `$avatar <url>` directives from fact facts, replacing the previous "tagged" message format (`**CharacterName:** text`)
- **Condition evaluation per entity:** Rather than single LLM call, the architecture evaluates each entity's `$respond` directive independently; only responding entities get included in LLM context
- **Response architecture:** Single combined LLM response (not separate messages per entity), with webhook dispatch handling the per-entity formatting

**Features Explored:**

- Handler.ts terminology audit: removing "character" language to prevent LLM realization of system architecture
- `/bind` and `/unbind` commands: redesigned for multi-entity workflows (additive binding, explicit unbinding)
- Fact directives: `$respond`, `$if`, `$avatar` parsing and evaluation in expression evaluator
- Reply condition logic: allowing default replies when message is directed to the entity's name
- Scope hierarchy: binding scope (guild/channel/user level) and permission checks on entity modifications
- Webhook caching: per-channel webhook reuse with different username/avatar per entity

**Notable Technical Threads:**

- Expression evaluator (`$if` conditionals) deep-dive: understanding how facts like `$if mentioned: $respond` control bot participation
- LLM response length limiting: maxTokens configuration for response generation
- Message history defaults and context truncation ("... (elided) ..." formatting for Discord's 2k character limit)
- Fact tool modifications: add_fact, update_fact, remove_fact execution and validation within LLM handler
- Entity permissions: created_by tracking, permission checks on /edit, /view, /delete commands, DM error reporting to entity owners

**Session Pattern:** Alternating between agent exploration (full codebase reads, data flow analysis) and small planning sessions. Many agent "Warmup" sessions (minimal real work) interspersed throughout the day, suggesting either test/orchestration activity or context-building between longer exploration runs.
