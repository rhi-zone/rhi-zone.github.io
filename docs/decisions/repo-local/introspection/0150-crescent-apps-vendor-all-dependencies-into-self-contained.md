# ADR-0150: Crescent apps vendor all dependencies into self-contained tarballs; security via explicit capability grants, not a package manager

- Status: Accepted
- Date: 2026-05-29

**Context.** Crescent shifted from a general LuaJIT platform into a portable application platform whose first apps (card, library browser, CCv2 adapters) needed to run on minimal installs. Apps are distributed as tarballs (source bundled in PNG metadata). Two coupled questions were forced: how apps obtain their dependencies (a package manager vs. self-contained bundling, and whether apps may depend on external/system libraries), and how shipping source code can be made safe.

**Decision.** First-party apps (card, library, adapters) vendor ALL dependencies (base64, json, reactive, lib.* modules) into their tarballs under a `_vendored/` root, so they run as self-contained units on minimal Crescent installs with no required external library dependency. The host provides fallback `lib.*` modules only as an optional convenience; the first-party suite always bundles to prevent silent breakage. Loading uses standard `require()` with the tarball-relative root as namespace — no symlinks or path manipulation. Security comes from explicit capability grants at platform load time (the platform validates required caps before running), not from sandboxing dependency versions; this is what makes shipping source code in PNGs acceptable. Third-party and first-party apps share no runtime contract beyond capabilities plus stdlib; `_vendored/` is the first-party convention, not mandatory for third-party.

**Alternatives rejected.**
- *A package manager that resolves and sandboxes dependency versions* — Rejected in favor of self-contained vendored tarballs that work on minimal installs; security is handled by explicit capability grants, not by sandboxing dependency versions
- *Apps depend on external/system libraries provided by the host* — Risk of silent breakage when host libraries differ or are missing; the first-party suite must remain portable and reproducible, so it always bundles even though host fallback lib.* modules exist

**Consequences.** Every app must vendor its deps and is not directly executable (requires platform loading). Apps cannot rely on a shared dependency runtime contract beyond caps + stdlib. The platform's capability-grant model becomes the security boundary. `_vendored/` is the first-party convention only. Open at the time: how to enforce that SQLite writes include app_id (deferred to runtime validation in the caps.db API).
