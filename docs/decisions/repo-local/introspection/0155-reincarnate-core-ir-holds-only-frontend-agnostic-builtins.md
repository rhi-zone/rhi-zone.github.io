# ADR-0155: Reincarnate core IR holds only frontend-agnostic builtins; operators and backend-varying logic decompose out of core

- Status: Accepted
- Date: 2026-05-29

**Context.** Reincarnate's type-inference cleanup matured into an architectural conversation about where operators and overload resolution belong in the compiler pipeline. After driving type errors down sharply (7,531 errors, a 72% reduction), the question of what the core IR should contain became load-bearing, forcing a decision on what belongs in core IR versus backend AST: whether arithmetic/comparison/string operators should be core::Op variants or decompose to specialized builtins.

**Decision.** Operators do not belong in the core IR; arithmetic and string operations decompose to specialized builtins (e.g., builtin.add_i32, builtin.add_f64; string manipulation like rsplit_once lives in builtins, not IR string encoding), not core::Op variants. Overload resolution is frontend work, not core-IR work; core only sees specialized builtins. The governing principle: anything that varies by backend (operators, visibility, method dispatch) is backend AST, not core IR. Type::Unknown and Type::Var are semantically distinct: Type::Unknown denotes frontend inference failure (gave up), Type::Var is an inference variable (GML DataType::Variable maps to Type::Var, not Unknown). The project entered a 'minimize core' phase, moving Expr::Binary/Expr::Unary to the TS backend and promoting BoolAnd/BoolOr to control-flow variants.

**Alternatives rejected.**
- *Keep operators as first-class primitives in the core IR (core::Op variants) with overload resolution handled at the core level* — Consensus was No; operators decompose cleanly to specialized builtins and overload resolution is conceptually frontend work, so keeping them in core bloats the IR the 'minimize core' phase is trying to shrink. Anything that varies by backend belongs in backend AST, not core IR.
- *Encoding string manipulation in core IR string operations* — String manip (rsplit_once, etc.) definitely belongs in builtins, not IR string encoding.

**Consequences.** The core IR is deliberately minimized and backend-agnostic; binary/unary expression handling and operator decisions live in the TS backend rather than core, and AST-rewriting passes move to backends. Boolean operators become control-flow variants. The principle (backend-varying logic is backend AST, not core IR) is stated as auditable across sibling IRs (moonlet, crescent). Open: NaN/comparison semantics (whether !(a < b) is equivalent to a >= b); parametric polymorphism (generic `array.get<T>()`) and _any IR dispatch semantics remain deferred pending an IR-extension design discussion.
